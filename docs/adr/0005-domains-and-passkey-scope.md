# The site on v2.sidequest.exchange, the gateway on agents.v2.sidequest.exchange, passkeys scoped to sidequest.exchange

Until now every stage ran on its `workers.dev` hostnames, and the website's way to the agent gateway took two deploys (the gateway needs the core's URL, the edge needs the gateway's). [ADR-0003](0003-nostr-native.md) decision 4 gives people without a Nostr signer a key derived from a passkey (WebAuthn PRF); a passkey is bound to a relying party ID, which is a domain, so the domain had to be chosen first. Kris decided both on 13 November 2026. The zone `sidequest.exchange` is on Sidequest's Cloudflare account; v1 runs at its apex.

## Decisions

1. **The site is `v2.sidequest.exchange`**, a Worker custom domain on the edge Worker. The `preview` stage takes it now.
2. **The gateway is `agents.v2.sidequest.exchange`**, a Worker custom domain on the gateway's Worker. A second-level subdomain is not covered by the zone's Universal SSL certificate (`*.sidequest.exchange` covers one level), but that does not matter here: creating a Workers custom domain issues an Advanced Certificate for that exact hostname, multi-level subdomains included, with no Advanced Certificate Manager subscription (Cloudflare, "Workers › Custom Domains › Certificates", checked 13 November 2026). No other name was needed.
3. **Both are stage settings from the deploying shell**, `SIDEQUEST_SITE_DOMAIN` and `SIDEQUEST_GATEWAY_DOMAIN` (`packages/server/src/StageDomains.ts`), attached with the pinned Alchemy's `domain` prop on `Cloudflare.Worker` (it puts the hostname through Cloudflare's `PUT /accounts/:account/workers/domains`, which creates the DNS record and the certificate, and makes `https://<domain>` the Worker's `url`). Unset, a stage stays on `workers.dev`, as local and test stages do. With them set, every URL is derived before anything deploys: the core URL the gateway calls and verifies NIP-98 for (`https://v2.sidequest.exchange`), the gateway URL the edge proxies to and the agents page shows (`https://agents.v2.sidequest.exchange`). One deploy configures both; `SIDEQUEST_GATEWAY_URL` is only for a stage without a gateway domain.
4. **The `workers.dev` hostnames stay on** for now: the rehearsal scripts and the evidence name them. On the site's `workers.dev` hostname, reads and publishing signed events work as before (each request carries its own signature; nothing reads the origin). The agents page does not: the gateway accepts a NIP-98 authorization through the core's proxy for exactly one core URL, the site's domain, so on any other hostname the page calls nothing and links to the domain instead. The gateway's own `workers.dev` hostname keeps working as an OAuth server of its own (the issuer is the origin a request came to, and tokens are bound to that origin's `/mcp`); the agents page shows MCP clients the domain's URL.
5. **The passkey relying party ID is `sidequest.exchange`**, the registrable parent, not `v2.sidequest.exchange`. It is a stage setting too (`SIDEQUEST_PASSKEY_RP_ID`; unset, passkeys are not offered), and a page offers passkeys only on a hostname within it, so the site's `workers.dev` hostname never does. Keys made on `v2.` keep working if the site moves to the apex.
6. **The derivation**, version 1 (`packages/nostr/src/PasskeyKey.ts`): the passkey's PRF is evaluated at `SHA-256("sidequest/nostr-key/v1")`; its 32-byte output is the input key material of HKDF-SHA256 with an empty salt and the info `sidequest/nostr-key/v1/secp256k1/<counter>`, 32 bytes long; the first candidate, from counter 0, that read big-endian lies in `[1, n − 1]` is the secret key. The key is never stored: it is derived again by a passkey assertion whenever a tab needs it, and `localStorage` keeps only `{signerKind: 'passkey', pubkey, credentialId}`. Any change to these parameters is a new version and a new key.
7. **A passkey that cannot derive is never kept silently.** Where the browser says beforehand that it lacks PRF, no passkey is made; where one was made and gives no PRF output, the person is told so plainly, the passkey's provider is told it is of no use (WebAuthn's Signal API, where the browser has it), and the in-browser key with its mandatory NIP-49 backup is offered instead.
8. **A backup is still offered.** After a passkey key is made the person takes an encrypted NIP-49 backup of it, or declines it by its own button, with the consequence stated: a lost or unsynced passkey loses the key. A linked wallet can always be linked to a new key (ADR-0003's recovery path).

## Consequences

- **Every `sidequest.exchange` subdomain is inside the key's security boundary.** A page on any hostname within the relying party ID (v1 at the apex, `dev.`, `media.`, `agents.v2.`, and any added later) can ask the browser for the same passkey with the same PRF input and derive a person's key, if it gets a person to approve one passkey prompt. A script injected into any of them could do that. Mitigations: the gateway's consent page sends a nonce-only CSP and loads no third-party script; the website's CSP stays `script-src 'self'`; v1 and the other hostnames must be treated as able to sign as every passkey user.
- **`/.well-known/webauthn` (related origins) is not needed**: every origin that uses the passkey is within the registrable domain it is scoped to.
- **Leaving `sidequest.exchange` entirely breaks passkey keys**: a passkey cannot be used for another relying party ID. Recovery is the NIP-49 backup, or a new key the person's wallet is linked to.
- **HSTS stays `max-age=31536000` on the edge**, without `includeSubDomains` or `preload`: the zone's apex and other hostnames are v1's and other projects', which this stack does not control. The gateway sends no HSTS header of its own.
- **Nobody verifies the assertion.** No server is part of the passkey ceremony: the challenge is random and the signature unchecked, because the PRF output, which only the authenticator computes and only after user verification, is all the key depends on.
- **Not proven**: real passkey providers (iCloud Keychain, Google Password Manager, Windows Hello, hardware keys) and browsers other than Chromium. Chromium's virtual authenticator proves the flows; a credential copied to another virtual authenticator over DevTools carries no PRF secret, so "another device" is proven with the same authenticator and the browser's storage wiped.
