# Status

- **Phase:** 2 ([roadmap](ROADMAP.md), [phase 2 spec](PHASE-2.md)). Sidequest is one system on signed Nostr events: the index, the fold, the escrow and its settler, the agent gateway and encrypted rooms. Phase 1's server-authoritative code (accounts, wallet sign-in, sessions, the model on Durable Objects, the core's MCP and OAuth) is deleted. The phase 2 technical gate has passed on Arc testnet for four of its five cases; the fifth (buyer reclaim after expiry) has passed only on a local chain. The market gate (an outside agent completes a hire) is open.
- **Source:** bootstrapped from Styld v2 commit `d0663c3` on 2026-10-29. No Sidequest V1 or Nod code has been ported.
- **Contract:** `SidequestOperator` v2 (delivery delegation) is deployed on Arc testnet (chain 5042002) at `0xA515f69EcAE571B1c7BC0911b3D1550f9eDb974b`, in block 72190184 (`0x44d88e8`), with a 500 bps fee to a throwaway test treasury. It is unaudited and exists on no other chain. It supersedes v1 at `0x979Ef80b97702ebCFCf6b0D9f9fc015C50C15a99`, which stays on chain unused.
- **Mainnet:** none. [MAINNET-READINESS.md](MAINNET-READINESS.md) (2026-11-13) lists what stands before one; blockers are the operator's audit, a Safe arbitrator and treasury, a production stage with remote deploy state, gateway secret rotation, alerts and legal review. Arc mainnet (chain 5042) is live but has no commerce-payments escrow; Base mainnet has the same escrow bytecode at the same addresses (fork-checked 2026-11-13). A stage names its chain (`SIDEQUEST_CHAIN`, default Arc testnet); mainnets are refused at deploy and by the Worker unless `SIDEQUEST_ALLOW_MAINNET` is the exact phrase for that chain, and the operator's deploy script needs its own phrase per chain id.
- **Preview:** Alchemy stage `preview`, deployed from the build box, at `https://v2.sidequest.exchange` with its agent gateway at `https://agents.v2.sidequest.exchange`, at release `98abaeb` on 2026-11-13, with testnet settlement on operator v2. Preview evidence says nothing about production.

## What is built (2026-11-13)

People are Nostr keys with a linked wallet; there is no account, session or cookie anywhere. The website's identity page links a key and a wallet; its home page, listings, requests and job pages run on signed events and the index; the job page carries the money steps (fund, deliver, approve, reject, review), each a wallet signature the API relays; the agents page runs on the agent gateway through the edge's `/gateway` proxy; the inbox is worked out in the browser. The server renders nothing personal.

Checked on the preview (2026-11-13, release `3a268ff`, from a script, not a browser): a signed profile, request and proposal published through `POST /api/events` and read back as a person and a job in stage `proposed` from the deployed D1; the relay pipe carrying a subscription to two public relays (nos.lol, relay.primal.net); a pipe from another origin refused.

The agent gateway (roadmap slice 8, [README](../apps/gateway/README.md)) reaches the core only through its public API. An operator's key makes an agent there (NIP-98), grants it with a signed event published through the core, and consents to an MCP client on the gateway's own page; the agent then signs as its own key under that grant, which the gateway re-reads from the index at most every 30 seconds. Its tools: whoami, search_listings, list_open_requests, get_job, get_person, payment_status, propose, withdraw_proposal, accept, deliver, delivery_delegation, the room tools, and x402_quote and x402_receipt. The fold counts an agent's proposal, accept, statement and delivery note as its operator's when the grant it names is that operator's, for that key, has the action's scope, holds the event's `created_at` in its window and is not revoked (a revoked grant authorises nothing, whenever the revocation arrived; only the funded proposal keeps its operator as the worker, because the chain's money is never undone). The job page shows an accept by the buyer's agent as such, and an accept by a key the buyer granted that does not count as that agent's suggestion, which the buyer accepts in one click. Unless the operator's wallet delegated the job's delivery to the agent's key, the agent's delivery note comes with the typed data the operator's wallet must sign.

Not proven: passkey-derived keys with a real passkey provider (iCloud Keychain, Google Password Manager, Windows Hello, a hardware key) or in Firefox or WebKit, and the same passkey on a second device (Chromium's virtual authenticator does not carry a credential's PRF secret to another); rooms on the deployed gateway; a real MCP client (claude.ai, ChatGPT, Cursor) or NIP-07 extension on its consent page; a real public inbox relay (with or without NIP-42), a real NIP-07 extension's `nip44`, Firefox and WebKit, and an outside NIP-17 client reading a room's text; the index's own connections to relays from a deployed Worker (no relay is configured); the pipe's per-address bounds on Cloudflare, where each isolate counts alone; a real Nostr extension or wallet on the identity page; whether public relays keep Sidequest's kinds. A contract wallet's link is stored as unverified: checking it needs a chain call the index does not make.

## Gate evidence

### Phase 2 (2026-11-13)

`bun run gate:rehearse` (`tools/rehearsal/GateRehearsal.native.test.ts`) deploys the core and the agent gateway together in local workerd, each its own Worker and D1, the gateway knowing only the core's URL. The buyer is a fresh Nostr key with a linked wallet, acting over HTTP (`POST /api/events` and the escrow endpoints). The worker is a fresh Nostr key that makes an agent at the gateway (NIP-98), grants it `propose` and `deliver` with a signed grant published through the core, and consents to an MCP client over OAuth; the agent finds the request (`list_open_requests`), proposes (`propose`, paying the worker's linked wallet) and delivers (`deliver`), and the fold counts its events as the worker's. Wallets sign only money; the relayer pays all gas. Money's stage is read from the index's fold, fed by the chain log poller and the settler on the API Worker's minute Cron Trigger, which fires in the local runtime; nothing triggers them by hand. Until phase 1 was deleted this rehearsal was `gate:rehearse:events`; its evidence files still name it `phase-2-events-gate`.

The Arc testnet run, before phase 1 was deleted, is [evidence/2026-11-13-arc-testnet-events-gate.json](evidence/2026-11-13-arc-testnet-events-gate.json): 12 relayed transactions, all mined; each confirmed three blocks deep in 4 to 19 s; the 214 requests through the proxy all answered. It records which key signed each event (the buyer's key, the worker's agent's key under its grant) and each gateway call. The run did not include a browser or the website (the buyer used a script, not the job page), a real MCP client (claude.ai, ChatGPT, Cursor), rooms, or deployed Workers: both Workers ran in local workerd, and their Cron Triggers fired there, not on Cloudflare. The wallets were test keys. The Anvil column has been rehearsed again since the deletion; Arc testnet has not.

**Deployed stage.** With `REHEARSAL_TARGET` and `REHEARSAL_GATEWAY` set, `bun run gate:rehearse` (`tools/rehearsal/DeployedRehearsal.native.test.ts`) runs the same hires against a stage already on Cloudflare and deploys nothing: the core's public API, the gateway's operator API through the site's `/gateway` proxy (NIP-98 signed for that URL, as the website does), OAuth and MCP at the gateway's own URL. The stage relays and rules with its own keys; the rehearsal holds only the buyer's and the worker's wallet keys (and, for (b), the stage's arbitration Nostr key), and reads the chain for balances and confirmations. Before the buyer signs, every quote must name the expected operator, fee receiver, escrow, network and chain id; the run refuses a target whose status is not `sidequest-v2`. The run of 2026-11-13 against the preview at release `98abaeb` is [evidence/2026-11-13-preview-deployed-gate.json](evidence/2026-11-13-preview-deployed-gate.json): 417 requests to the stage, none rate limited, each recorded with its status and latency under the step it led to; each relayed step confirmed three blocks deep in 4 to 19 s, and the deployed chain log poller showed it in the index's fold 40 to 54 s later (once 114 s, a missed minute); the deployed settler's `refundUndelivered` (sent by the stage's relayer, read back from the payment status) was mined 122 s after (c)'s deadline. This proves the poller and the settler doing their work on Cloudflare's Cron Triggers, and the deployed gateway's operator API, OAuth and MCP tools. The preview's release does not yet name the operator in the payment status (added since, `operator` beside `escrow`); the run checked the operator in every quote and on chain instead. It did not include a browser or the website (the buyer was a script), a real MCP client app (claude.ai, ChatGPT, Cursor), or rooms; the wallets were test keys.

`bun run gate:rehearse:browser` (`packages/server/rehearsal/BrowserRehearsal.native.test.ts`) runs a hire released and one rejected on the website, by two people in Chromium with a test NIP-07 extension and a test wallet each, on Anvil only.

On 2026-11-13 Arc testnet made blocks 3.9 s apart on average, and up to 30 s apart while two of its validators proposed, against 0.55 s on 2026-11-12; a relayed step then took 6 to 37 s to be included and confirmed three blocks deep. The rehearsal waits for that confirmation on chain, recording how long it took, before it gives the stack its time to show the step.

## Not proven

- A real wallet (MetaMask, Rabby) in a browser, and the money steps on the deployed preview's website (the deployed gate drove them from a script). The website's money steps are proven only with a test wallet and a test NIP-07 extension in Chromium, against local workerd and Anvil.
- Reclaiming from the website: the job page tells a buyer whose authorization expired to call `reclaim` on the escrow it names, and builds no transaction.
- A third-party MCP client (claude.ai, ChatGPT, Cursor, Claude Code) connecting to the gateway over OAuth.
- The buyer's reclaim on a live chain.
- Deleting phase 1's Durable Object classes on a deployed stage: Alchemy's delete-class path is read from its source, not yet run against the preview.

## Known gaps

- The x402 rail (ADR-0006) is proven only on Anvil, against the reference seller (`examples/x402-seller`) and a facilitator written for the test; not with a hosted facilitator (Circle's settles on Arc testnet) or a real seller. Its fee and its networks beyond Arc testnet are Kris's decisions. The website shows how to pay and call; it does not pay.

- Disputes are settled by an arbitrator key Sidequest holds; they are not trustless until staked arbitrators exist, and a ruling sees no disclosed evidence yet.
- The API sends no CORS headers: a third-party web client on another origin cannot call it from a browser.
- No rate limiting on the gateway's OAuth endpoints (its MCP tools are limited per agent).
- A job funded by the first live run (`0x1546…`, 0.1 test USDC, operator v1) stays in the escrow on Arc testnet until the test buyer reclaims it after expiry.
- Deploy state is local to the build box, so only the build box can deploy (remote state options: MAINNET-READINESS §3.3).
- Nothing pages anyone: the logs carry `alert` annotations, and the settler warns each minute while the relayer's balance is low, but no alert rule reads them.
- The gateway's secret, which seals every hosted agent's key, cannot be rotated yet (design: MAINNET-READINESS §2.4).
- Events by id are now cached for an hour, not a year, so a hide reaches caches; this changes the preview's cache headers on its next deploy.
- The Slovenian copy has not been reviewed by a native speaker.
